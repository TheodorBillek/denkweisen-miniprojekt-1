Namen sind doch einfach: Five bad forms and a good one

1. SQL Injection

This is a login form more than a contact form, but to be honest I got bored of writing only contact forms. So treat this as an admin login to the backend for all the contact forms, or whatever. I also ripped the CSS and a bit of the HTML from a template, and I may have forgotten to turn it into a contact form before moving on.

Anyway, we have a username and a password. The query in the backend looks something like this: 

const sql = `SELECT * FROM users WHERE username = '${u}' AND password = '${p}'`;

You can check it yourself at github.com/TheodorBillek/denkweisen-miniprojekt-1, or by viewing the page source (CTRL+U in Brave and Chrome, I think).

If you know anything about programming or cybersecurity, you'll see this is the insecure version of an SQL query. Without any checks, we paste two variables straight into the string, so an input like admin' -- can bypass the password check and log you in as admin. If you're a bit more creative, admin' OR 1=1 -- is always true and logs you in as admin too. This works because the username input closes the quote with ', and then -- is an SQL comment that removes everything after it. For the password, you can enter anything, since it's ignored.

2. All-in-One

Here we take in all the fields separately: Anrede, first name, last name and email. We even let people write their own Anrede. Then we chuck it all into one column, called full name, and save that. This makes personalised greetings hell. In this case we end up just going with "Sehr geehrte*r", and even that generic greeting isn't great. So all we end up with is a mess that rarely actually works.

3. Limited Anrede and Mismatch

Here we not only have two options for the Anrede, but we also check for "herr" while the field value is "Herr". That way, even if we would satisfy someone by having their Anrede, it still wouldn't pick the right one, and we end up addressing everyone with "Frau".

4. ASCII-Only

This one should speak for itself. If we try to enter a name like Jürgen, or a name in another alphabet such as 李, we just can't handle it. We live in the 21st century and should be able to handle a bit more than ASCII. The check in this form is a little cheaty: the default way we handle input would allow more than ASCII, so I just check with a regex whether the input is ASCII and deny it if it isn't.

5. Splitting Name

Another simple one. Here we combine first and second name into one full name in the SQL database, and when we want to greet someone, we split it: [0] for the first name and [1] for the second. That's also quite bad, because what if someone is called John Hammond Peter? You could say just use a dash instead. Firstly, that would be a different name. Secondly, it breaks my code for some reason XD

6. Good Design

This is a version of a good contact form, as conceived by my colleague. It asks for a legal name because the hotel needs to compare the registered name to an ID, needs to be able to check who they are dealing with, and is sometimes obligated to know who they are dealing with due to "Know your customer" laws.

But we have an option to change how the person wants to be addressed, in case they don't want to be addressed with their legal name. We also give them a range of Anreden, including none.

Furthermore, we allow all characters, and all fields are stored separately in separate columns. We never assume that we can split a name, or that people have 1, 2 or any specific number of names. The only thing we don't support is people without names, but even then they would be able to write in how they wish to be addressed. We also have a requirement that they need to have some form of legal ID, but that is more of a quirk of the legal system, less of our form.
